📊 How Instance Data Flows During XML Generation

This explanation is written for beginners. Think of it like a recipe: ingredients (data) come from a storage place (database), get processed (XML generation), and become a final dish (XML file).

🎯 The Big Picture

Instance Data Journey:

Database → Backend reads it → Process it → Create XML → Return XML

📍 Step-by-Step Breakdown

1 User Clicks "Generate XML"

Frontend sends a request to the backend saying "Generate XML for these instances"

File: generate.js (lines 612-624)

POST /api/generate Body: { projectName: "AS01", instances: [ { cmType: "CM_AO", instanceName: "CM_A01", samplingTime: "1000" } ] }
2 Backend Receives Request

The generate.js file receives the request in the runGeneration function.

Function: runGeneration(db, body, onProgress) (line 27)

What happens:
  • Extract project name and list of instances
  • Look up the project in the database
  • Get instance-specific data from the database
3 Reading Instance Data from Database

The backend queries a database table called project_instances to get all the saved data about each instance.

Database Table What It Stores
project_instances • instance name
• CM type
• sampling time
• enabled blocks
• connections
• role assignments
• folder location
instance_matrix_overrides Custom values for matrix instances (user overrides)
lib_cm_types The "template" for each CM type (blocks, variables, messages)

File: generate.js (lines 40-165)

4 Resolve Each Instance

For each instance, the backend calls resolveInstance() function to:

  • Load the CM type template (like a blueprint)
  • Get all the blocks and variables for that CM type
  • Combine template data with instance-specific customizations

Function: resolveInstance(inst) (lines 322-413)

// Instance data being resolved: { instanceName: "CM_A01", cmTypeName: "CM_AO", samplingTime: "1000", enabledBlocks: ["AIF_FRONT", "CSF"], roleAssignments: { ... } }
5 Load CM Type Template

The backend queries the library to get the CM type's structure (what blocks and variables it has):

SELECT * FROM lib_cm_types WHERE name = ? // Gets the CM_AO template structure SELECT * FROM lib_blocks WHERE cm_type_id = ? // Gets all blocks in CM_AO (like "AIF_FRONT", "CSF", etc.) SELECT * FROM lib_variables WHERE block_id = ? // Gets variables for each block

Queries: lines 262-283

6 Combine Data: Template + Instance Customization

Now the backend has:

  • Template: What a CM_AO should look like (from library)
  • Instance Data: How THIS specific instance is customized

Example combinations:

Data Type From Template From Instance Final Result
Sampling Time "1000" "500" "500" (instance wins)
Blocks 10 blocks User selected 5 Only 5 blocks
Role Assignments Generic Custom roles Custom roles
7 Generate XML

Now the backend calls generateXML() with all the resolved instance data.

File: xmlGenerator.js (line 563)

The XML generator creates:
  • <ControlModule> - one per instance
  • <Block> - one per enabled block
  • <Variable> - one per variable in each block
  • <Message> - alerts/warnings for the instance
  • <IOTag> - hardware connections
8 Return XML to User

The XML is sent back to the frontend and the user can download it.

💾 Database Tables Used During Generation

Table Name Purpose Instance-Specific?
project_instances Stores each instance's settings (name, CM type, sampling time, etc.) ✅ YES
lib_cm_types Template/blueprint for CM types ❌ NO (shared template)
lib_blocks Available blocks in each CM type ❌ NO (shared template)
lib_variables Variables in each block ❌ NO (shared template)
instance_matrix_overrides Custom values user set for matrix instances ✅ YES
instance_derived_values Calculated/special values for instances ✅ YES

🔄 Simple Analogy

Think of it like ordering a pizza:
  • Template (CM Type): The basic pizza recipe (crust, sauce, cheese)
  • Instance Data (project_instances table): Your specific order - "add pepperoni, no onions, extra cheese on the left side"
  • Customizations (matrix overrides, role assignments): Special requests - "make it spicy, cut into 8 slices"
  • XML Generation: The pizza maker combines the recipe with your customizations and makes your pizza
  • Result (XML): Your customized pizza delivered to you

📝 Key Takeaways

  • Data Storage: Instance-specific data lives in the database, in the project_instances table
  • Data Retrieval: When generating XML, the backend queries the database using SQL to get instance data
  • Data Combination: The backend combines the template (CM type) with instance-specific customizations
  • XML Creation: The xmlGenerator uses this combined data to create XML elements
  • Main Files:
    • generate.js - handles the request and loads data from database
    • xmlGenerator.js - creates the actual XML using that data
