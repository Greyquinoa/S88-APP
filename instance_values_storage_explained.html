💾 Where Instance-Specific VALUES Are Stored

Instance values are scattered across 5 different database tables. Each table stores different types of values for the same instance.

📊 Quick Reference Table

Database Table What Values It Stores Example Value
project_instances Basic instance settings sampling_time: "1000"
project_cmt_profiles Which blocks are enabled enabled_blocks: ["AIF_FRONT", "CSF"]
instance_ios Hardware signal connections signal_name: "PLC_Pressure_01"
instance_derived_values Calculated values from IO lists value: "100.5"
instance_matrix_overrides Custom matrix cell values cells: {1: {"column1": 5}}

1️⃣ project_instances Table

project_instances - Main Instance Data

Purpose: Stores the core settings for each instance

instance_name
Name of the instance (e.g., "CM_A01")
cm_type
What type of CM is this (e.g., "CM_AO", "CM_AV")
sampling_time
⭐ INSTANCE VALUE: How often to sample (e.g., "1000" = 1 second)
user_project
Which user project this instance belongs to (e.g., "AS01")
role_assignments
⭐ INSTANCE VALUE: Custom role settings stored as JSON
connections
⭐ INSTANCE VALUE: Hardware connection rules stored as JSON
folder_id
Where this instance is located in the hierarchy
hw_controller_id
Which hardware controller owns this instance
Example Row: { id: 1, instance_name: "CM_A01", cm_type: "CM_AO", sampling_time: "1000", ← INSTANCE VALUE user_project: "AS01", role_assignments: '{"R001": "Tank01"}', ← INSTANCE VALUE (JSON) connections: '[{...}]', ← INSTANCE VALUE (JSON) folder_id: 5, hw_controller_id: 2 }

2️⃣ project_cmt_profiles Table

project_cmt_profiles - Enabled Blocks Per CM Type

Purpose: Stores which optional blocks are enabled for each CM type

project_id
Which project this belongs to
cm_type
CM type name (e.g., "CM_AO")
enabled_blocks
⭐ INSTANCE VALUE: List of enabled blocks stored as JSON array
Example Row: { project_id: 1, cm_type: "CM_AO", enabled_blocks: '["AIF_FRONT","CSF","GMP","IF_BACK"]' ← INSTANCE VALUE }

3️⃣ instance_ios Table

instance_ios - Hardware Signal Connections

Purpose: Stores which hardware signals are connected to each block/variable

instance_name
Which instance this IO belongs to
block_name
Block name (e.g., "AIF_FRONT")
var_name
Variable name in that block
signal_name
⭐ INSTANCE VALUE: Hardware signal connected (e.g., "PLC_Pressure_01")
signal_type
⭐ INSTANCE VALUE: Type of signal (e.g., "analog", "digital")
hw_signal_id
Reference to the actual hardware signal in the hardware library
status
Is this a real connection or dummy? ("real" or "dummy")
Example Rows (for instance "CM_A01"): { instance_name: "CM_A01", block_name: "AIF_FRONT", var_name: "Pressure", signal_name: "PLC_Pressure_01", ← INSTANCE VALUE signal_type: "analog", ← INSTANCE VALUE status: "real" } { instance_name: "CM_A01", block_name: "CSF", var_name: "Temperature", signal_name: "PLC_Temp_02", ← INSTANCE VALUE signal_type: "analog", ← INSTANCE VALUE status: "real" }

4️⃣ instance_derived_values Table

instance_derived_values - Calculated Values

Purpose: Stores calculated values for matrix connections or IO-based calculations

instance_name
Which instance this value belongs to
to_var_name
Variable receiving the value
symbol_name
Symbol from the hardware library
column_name
Matrix column name
value
⭐ INSTANCE VALUE: The calculated/resolved value (e.g., "4.5")
override_value
⭐ INSTANCE VALUE: User override (if user manually changed it)
status
Was this value resolved? ("resolved" or "unresolved")
Example Row: { instance_name: "CM_A01", to_var_name: "OutputValue", symbol_name: "PLC_Tank_Level", column_name: "ScaleFactor", value: "100.5", ← INSTANCE VALUE (calculated) override_value: "95.0", ← INSTANCE VALUE (user override) status: "resolved" }

5️⃣ instance_matrix_overrides Table

instance_matrix_overrides - Custom Matrix Values

Purpose: Stores custom values users entered for matrix instances

instance_name
Which instance this override belongs to
enabled
⭐ INSTANCE VALUE: Is this override active? (true/false)
cells
⭐ INSTANCE VALUE: Custom cell values stored as JSON
Example Row: { instance_name: "ValveMatrix_01", enabled: true, ← INSTANCE VALUE cells: '{ "1": {"Open": 50, "Close": 100}, "2": {"Open": 60, "Close": 110} }' ← INSTANCE VALUE (JSON) }

🔍 How These Values Are Retrieved During XML Generation

Step-by-step retrieval:
1. Get Instance Metadata
SELECT * FROM project_instances WHERE instance_name = ?
→ Gets: sampling_time, role_assignments, connections, folder_id, etc.
2. Get Enabled Blocks
SELECT enabled_blocks FROM project_cmt_profiles WHERE cm_type = ?
→ Gets: which blocks to include in XML (e.g., ["AIF_FRONT", "CSF"])
3. Get Hardware Connections
SELECT * FROM instance_ios WHERE instance_name = ?
→ Gets: signal_name for each variable (what hardware it connects to)
4. Get Calculated Values
SELECT * FROM instance_derived_values WHERE instance_name = ?
→ Gets: calculated values and overrides
5. Get Matrix Overrides (if matrix instance)
SELECT * FROM instance_matrix_overrides WHERE instance_name = ?
→ Gets: custom cell values for matrix instances
6. Combine All Values
Create a complete picture of the instance with all its values
→ Then pass to xmlGenerator to create XML

🎯 Key Takeaways

📌 Instance Values Are Spread Across Multiple Tables:
  • project_instances → Basic settings (sampling time, roles, connections)
  • project_cmt_profiles → Which blocks to include
  • instance_ios → Hardware signal connections
  • instance_derived_values → Calculated/resolved values
  • instance_matrix_overrides → Custom matrix cell values
💡 Why Multiple Tables?
  • Separation of Concerns: Each table holds one specific type of data
  • Flexibility: Easy to add/remove values without changing the main table
  • Performance: Only query the tables you need
  • Clarity: Clear what each table stores
⭐ When Generating XML:
  • generate.js queries ALL these tables to get complete instance data
  • Combines data from all tables into one object
  • Passes the combined object to xmlGenerator.js
  • XML generator uses all these values to create the XML file
